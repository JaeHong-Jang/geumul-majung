# 그물마중 백엔드 설계 (잔재미 위에 얹는 부분)

2026-11-27 기준(같은 날 2차 조사를 반영해 2·3·4·6·10절을 고침). 이 문서는 설계안이고 아직 코드로 옮기지 않았다.
가격 구조, 처리비 화면 표시, 화면 문구는 다른 담당이 고치는 중이라 여기서는 맞닿는 지점(9절)만 정한다.

표기: **[사실]** 공개자료 원문에서 확인, **[가정]** 팀이 정한 값, **[미확인]** 공개자료로 확인하지 못함.
근거 원문은 `대학창업대전/05_리서치/research_notes/그물마중 수거 구조 확인/` 노트 3개(현장, 절차·서식, 다른 지역·업체), `대학창업대전/05_리서치/research_notes/그물마중 앱 데이터 구축/` 노트 3개, `대학창업대전/01_전략/보령 삽시도 폐어망 재활용 사업화 및 실증안.md`에 있다.

## 0. 한눈에

1. 잔재미는 "공장이 마대를 등록 → 판매 글 → 구매자가 주문"의 **두 당사자, 한 번의 육상 운송** 구조다. 폐어구는 **더미로 쌓였다가 한꺼번에 나가고, 돈 내는 기관과 처리업체가 계약으로 묶여 있고, 해상과 육상 두 번 옮겨지고, 무게는 육지에서야 재고, 도착해서 일부만 재활용된다.**
2. 삽시도 집하장에는 톤백도 마대도 아닌 **포장 없는 더미**가 '해양쓰레기'와 '폐어구' 두 칸에 쌓여 있다. 재활용업체는 이렇게 섞인 집하장 물량을 대체로 받지 않는다. 그래서 앱이 기록할 핵심은 "몇 마대"가 아니라 **"더미에서 무엇을 얼마나 떼어 놓았고 어떤 상태인가"**다.
3. 처리장은 건마다 고르는 것이 아니라 **낙찰 업체의 처리업체로 계약 기간(약 1년) 동안 정해진다.** 그래서 기본 흐름은 "계약된 업체와 인수 조건을 미리 맞추기"이고, 여러 업체 견적 비교는 계약 밖 물량이나 다음 계약 준비용이다.
4. 기존 표(`bags`, `listings`, `orders`)는 그대로 두고 옆에 표를 붙인다: 묶음 상세, 반출 계약, 반출편, 반출분, 운반 구간, 견적, 인수 결과, 문서 스캔.
5. 사진과 음성은 한 요청으로 같이 받는다. 숫자는 사람 말에서만, 사진에서는 종류·부착물·오염·섞임만 읽는다. 현장에는 저울이 없으므로 등록 무게는 모두 어림값이고 정산 무게는 육지 계량증명서에서만 온다.
6. 문서 사진은 "옮겨 적기 → 칸 채우기 → 코드 검산 → 사람 확인" 순서로 초안을 만든다. 1순위 서류는 계량증명서, 어구 인수인계 명세서(법정 서식), 폐어구 관리대장(법정 서식)이다.

## 1. 법령 검색은 지금 어떤 방식인가

**넓은 뜻의 RAG에서 '찾기'만 하고, '쓰기'는 사람이 미리 써 둔 문장을 쓴다.** 임베딩(벡터) 검색은 없다.

| 기능 | 찾는 방법 | 답을 쓰는 주체 | 위치 |
|---|---|---|---|
| 앱 대화의 법 질문 | 질문과 조문의 한글 글자쌍 겹침 수 + `law_plain.json` 낱말이 질문에 있으면 3점 + "제N조"가 맞으면 3점. 1등 점수의 절반 미만은 버림. 최대 3개 | `law_plain.json`의 쉬운 문구(headline, body)를 그대로 주장으로 냄. LLM은 요약 문장만, 주장에 없는 숫자를 쓰면 게이트가 버림 | `app/agents/assistant.py` `law_matches`, `law_claims` |
| 자료 질문(`/v1/knowledge/ask`) | 글자 두 개 단위 BM25. `KNOWLEDGE_DIR` 폴더가 있어야 켜짐 | LLM이 찾은 자료만 근거로 씀. 자료에 없는 숫자나 출처 번호가 있으면 정해 둔 문구로 대체 | `app/tools/knowledge.py`, `app/features/knowledge/router.py` |
| 주문 법 체크리스트 | 검색 없음. 폐기물 코드로 조문 id를 코드가 고름 | 코드 | `app/agents/review/regulation.py` |

이번에 조문을 23개에서 57개로 늘렸지만 방식은 그대로다. 조문이 57개뿐이라 글자쌍 검색으로 충분하고, 조문마다 사람이 쓴 쉬운 문구가 붙어 있어 지어내기가 구조적으로 막힌다. 수백 개로 늘지 않는 한 벡터 검색으로 바꿀 이유가 없다.

`KNOWLEDGE_DIR` 자료는 공장 22만 곳 기록이라 폐어구와 맞지 않는다. 폐어구용 자료(충남연구원 보고서, 과업지시서, 조례)로 다시 만들지는 4단계에서 정한다.

## 2. 폐어구는 실제로 어떻게 수거되나

```
어민 → 섬 집하장(보령시 소유, 더미로 쌓음)

            육지 공인 계량소에서 차량 단위 계량(공무원 입회) → 처리업체(소각 또는 재활용)
```

### 2.2 재활용이 안 되는 이유는 '섞임'이다

KMI 현장조사(2023, 재활용업체 4곳)와 업체 자료에서 확인한 것 [사실]:

- 재활용업체는 지자체·수협 집하장 물량을 대체로 다루지 않는다. 다른 쓰레기와 섞여 나와 선별비가 맞지 않기 때문이다.
- 바다에서 건진 것(침적·인양)은 펠릿 원료로 못 쓰고 열 회수만 된다. **쓰다가 내놓은 것인지 건진 것인지**가 갈림길이다.
- 온전해야 받는다. 엉켜서 자른 것은 성분비를 알 수 없어 받지 않는 업체가 있다.
- 자망은 뜸줄·발줄이 붙어 엉긴 채 들어오는 것이 문제다. 뜸줄만 떼어도 나일론 비율이 50%에서 80%로 오른다.
- 로프는 납심, PET 피복, 면사 감은 것, 해조류·어류가 붙은 양식 로프를 거절한다.
- 현장 분류는 **통발 / 어망 / 로프** 세 가지다(홍원항 안내문, 수협 수매 기준). 부표·스티로폼은 일반 해양쓰레기 쪽에 쌓는다.
- 자망의 나일론과 PE는 눈으로 가리기 어렵다. 재질은 어구 종류와 부위로 짐작한다(자망 그물감은 나일론, 뜸줄·발줄은 PP, 통발은 철 틀과 PE 그물, 로프는 대부분 PP).
- 업체가 반입 기준, 최소 물량, 포장 규격을 누리집에 밝힌 곳은 없다. 조건은 물어서 받아야 한다.

그래서 앱이 하는 일의 중심은 **"섞인 더미 중 어느 부분을 얼마나 손봐서 떼어 놓으면 계약 업체가 재활용으로 받는가"를 반출 전에 정하는 것**이다. 실증안의 "그대로 보낼 때와 떼어 보낼 때 비교"가 바로 이 지점이다.

### 2.3 단위

| 단위 | 뜻 | 기존 표 | 화면에 쓸 말(제안) |
|---|---|---|---|
| 더미 | 집하장 칸에 쌓인 전체. 섞여 있음 | 새 표 없이 반출분의 '남은 더미' 어림값으로만 기록 | 더미 |
| 묶음 | 더미에서 종류별로 떼어 놓은 한 덩어리(통발·어망·로프). 떼지 않았으면 '혼합' 묶음 하나 | `bags` + 새 `gear_lots` | 묶음 |
| 품목 줄 | 같은 폐기물 코드·등급 묶음의 합 | `listings` | 품목 |
| 반출분 | 한 반출편에 실어 보내는 전체. 차량 한 대분이 계량 단위 | 새 `shipments` | 반출분 |
| 인수 건 | 반출분 중 한 업체가 재활용으로 받은 부분 | `orders` + 새 `acceptances` | 인수 건 |

무게는 세 단계로 구분해 적는다: 눈대중 → 용기·차량 환산 → 계량증명서. 정산과 실적에는 계량증명서 값만 쓴다. 100L 마대 한 개 약 26~29kg, 수거차 한 대 약 4.25톤은 계산으로 얻은 [가정]이라 환산 기본값으로만 쓴다.

### 2.4 누가 무엇을 하나

| 주체 | 앱 계정 | 하는 일 | 기존 role |
|---|---|---|---|
| 집하장 쪽 담당(이장·어촌계·미화원 중 [미확인]) | 있음 | 묶음 등록(말+사진), 떼어 놓기 작업 기록 | `factory` 그대로 |
| 수거·처리 낙찰업체, 재활용업체 | 있음 | 받는 조건 등록, 견적 회신, 계량·검수 결과 입력 | `recycler` 그대로 |
| 조율 담당(우리 팀) | 있음 | 조건 확인, 반출편 일정 확인, 정산 비교표 | `operator` 그대로 |
| 발주 기관(보령시 해양정책과, 충남도, 공단) | 없음(이름과 계약만 기록) | 수거 지시, 검측, 대금 지급 | 새 표 `contracts` |
| 선박·차량 | 없음(이름·차량번호만 기록) | 운반 | 새 `shipment_legs` |

법으로 정해진 당사자 관계 [사실]: 집하장 물량을 맡기는 쪽은 시·군(또는 일을 넘겨받은 수협)이고, 받는 쪽은 그쪽이 계약한 허가·신고 업체다. 재위탁은 금지되고, 직접 운반하면 소량이라도 허가 대상이다. 우리 팀은 운반·보관·처리와 계약 당사자가 되지 않고 기록과 조율만 한다. 조율만 하는 일에 대한 당국 해석은 여전히 [미확인]이다.

보증금 어구 [사실]: 보령의 반납장소는 육지 한 곳(신흑동 2243-7 집하장)뿐이고 섬은 "가장 가까운 육상 반납장소로 안내"가 지침이다. 보증금 표식이 붙은 통발·자망·부표는 매칭에서 빼고 반납 경로를 안내한다.

### 3.2 반출분 상태

```
draft 작성 중 → requested 견적 요청 → quoted 회신 있음 → booked 업체·반출편 확정
→ loaded 선적 → landed 하역·육상 인계 → received 업체 도착 → inspected 검수 → settled 정산
```

- 어디서든 → `cancelled`. `booked`·`loaded` 전에 결항·연기면 → `held`(다음 반출편 지정 후 `booked`로, 견적 유효기간이 지났으면 `requested`로).
- 견적이 없거나 기한이 임박하면 → `fallback`(기존 승인 경로로 처리, 실증안 3절). 이것도 기록으로 남겨 비교 기준이 된다.
- 반출 시점은 우리가 정하지 못한다. 감독공무원의 수거 지시나 운반선 일정이 정해지면 `booked`로 가고, 그 전까지는 `draft`에서 묶음을 계속 더한다.
- 바꾸는 방식은 기존 `orders/state.py`와 같게 한다: 전이 표 + `UPDATE … WHERE status=이전 상태` + 이력 표.
- 주문(인수 건)은 `booked`에서 만들어진다. 반출분이 두 업체로 갈리면 주문이 둘이다(기존 `orders/batch` 사용). 주문의 기존 상태와는 이렇게 맞춘다: loaded→`dispatched`, landed→`picked_up`, received→`arrived`, inspected→`confirmed`.

## 4. 매칭

### 4.1 기본 흐름: 계약 업체와 조건 맞추기

처리장이 계약으로 정해진 물량(`route_mode=contract`)이 기본이다. 이때 '매칭'은 업체 고르기가 아니라 **묶음별 처리 방법 정하기**다.

| 단계 | 하는 일 | 근거 자료 | 누가 |
|---|---|---|---|
| ① 묶음 가르기 | 묶음마다 재활용 후보인지 코드가 표시: 건진 것, 자른 것, 섞인 것, 거절 사유가 있는 로프는 "열 회수·소각 쪽"으로, 보증금 표식은 "반납 경로"로 | `gear_lots` | 코드 |
| ② 손보기 제안 | 재활용 후보가 되려면 무엇을 떼야 하는지 표시(예: 자망의 뜸줄·발줄, 통발의 철 틀). 떼는 데 드는 시간도 같이 | `gear_lots.attachments`, 팀 가정 | 코드 |
| ③ 조건 확인 | 계약의 처리업체에 반출분 카드를 보내 "그대로 / 떼어서" 두 조건의 회신을 받음. 전화·문자 회신은 조율 담당이 입력 | `quotes` | 사람 |
| ④ 비교 | 조건마다 총비용과 재활용량을 계산 | `quotes.options`, `contracts.unit_rule` | 코드 |

계약서에 적힌 재활용 유인은 "재활용이면 처분부담금을 정산에서 뺀다" 하나다 [사실]. ④는 이 차이와 업체의 선별비·잔재 처리비, 섬의 작업 시간을 한 표에 놓는다.

### 4.1-2 넓힌 흐름: 여러 업체 견줘 보기

계약 밖 물량, 다음 해 계약 준비, 계약 업체가 재활용을 못 하는 품목에 쓴다(`route_mode=open`).

- 자격 거르기: 업체의 허가·신고 품목 코드에 그 코드가 있는가, 받는 재질인가, 가입 승인 상태인가(`companies.permit_codes`, `gear_recyclers.json`).
- 조건 맞춤: 업체가 올린 받는 조건(`buy_requests`)과 묶음을 견줘 "맞음·안 맞음·모름"을 이유와 함께 표시. 업체가 조건을 공개하지 않는 것이 보통이라, 모른다고 빼지 않는다.
- 업체가 견적 때 묻는 것(한울메탈 누리집과 KMI 조사): 품목·재질, 대략 물량(톤백·차량 대수 등 아는 단위), 차량 접근·상차 가능 여부, 일정과 정기 여부, 섞임, 부착물, 절단 여부, 건진 것인지, 생물·뻘·젖음, 로프 특이사항, 포장과 상하차 장비, 운반비·처리비 부담자. 반출분 카드가 이 12가지를 담는다.
- 후보: 기존 8곳(울산·부산·경주)에 더해 해양플라스틱재활용사업공제조합 회원 명단의 충남 예산군 ㈜현창에코(로프·어망) 등 서해안권 업체가 있다. 반입 조건과 섬 물량 인수 여부는 [미확인]이라 데이터에는 '조건 미확인'으로 넣는다.

### 4.2 총비용 식 (④)

```
총비용 = 인수 예상 kg × 인수분 단가 + 잔재 예상 kg × 잔재 처리 단가
       + 육상 운송비 + 도선료 등 실비 + 섬에서 추가로 드는 작업 시간 × 시간당 인건비
순절감 = 기존 방식 총비용(baseline) − 총비용 − 우리 운영료
```

- 처분부담금: 소각·매립분에만 붙는다. 금액은 `contracts.unit_rule`에서.
- 인수 예상 kg: 견적의 `accept`와 `max_kg`에서. 업체가 비율을 안 주면 그 업체의 지난 인수율(`acceptances` 평균), 이력도 없으면 "모름"으로 두고 세 경우(40%, 60%, 80%)를 나란히 보여 준다 [가정].
- 인건비·운영료·세 경우의 비율은 `harness.yaml` assumptions에 두고 주장에 "팀 가정" 근거를 붙인다.
- 줄 세우는 순서: 순절감 큰 순 → 인수 예상 비율 → 거리. 견적 유효기간이 지난 것은 맨 뒤.
- 어민의 무급 작업으로 생긴 차액을 절감으로 잡지 않도록 추가 작업 시간은 반드시 넣는다(실증안 3절).

### 4.3 모아서 최소 물량 채우기

기존 `bundling`은 "반경 안 같은 코드·등급"을 합친다. 섬은 직선거리가 뜻이 없다. 묶는 기준을 **같은 계약, 같은 반출편(또는 같은 달 같은 하역항)의 같은 종류**로 바꾼 흐름을 새로 둔다(기존 것은 그대로). 도서지역 계약은 여러 섬을 한 업체가 돌기 때문에, 삽시도 한 곳으로 모자랄 때 다른 섬의 떼어 놓은 어망을 한 차로 모을 수 있는지 보여 준다. 재생 나일론 쪽 수요는 한 번에 수십 톤 단위라 [사실] 모으기가 전제다.

### 4.4 반대 방향

업체가 받는 조건을 올리면(기존 `buy_requests`) 맞는 묶음이 등록될 때 업체에 알림이 간다. 기존 `want_match`가 재질·수량·가격을 견주는데, 여기에 부착물 허용과 날짜를 더한다.

### 4.5 하네스에 넣는 방식

- 새 에이전트 `gear_match`(`app/agents/trade/`), 새 흐름 `shipment_match`. LLM 호출 없음.
- 내는 주장 예: "받을 자격이 있는 업체 3곳 중 2곳 회신" (fact, 근거 input) / "울산 가 업체는 최소 물량 3톤, 이번 반출분 2.1톤으로 미달" (fact, 근거 input+calc) / "인수 60%로 볼 때 기존 방식보다 12만 원 적음" (estimate, 근거 calc+assumption).
- 기존 게이트(근거 없는 주장 차단, 주장에 없는 숫자 차단)를 그대로 지난다.

## 5. 사진과 음성을 함께 받는 입력

### 5.1 지금

- 음성: 서버 안 Whisper로 글로 바꿈 → `intake` 에이전트가 칸을 채움. 음성을 밖으로 보내거나 저장하지 않음.
- 사진: 저장만 하고 읽지 않음. `vision` 에이전트는 이름과 달리 입력한 품목 숫자만 계산한다.
- LLM 연결부는 글만 받는다(`chat(system, user, schema)`).

### 5.2 바꾸는 것

```
POST /v1/lots/intake   { audio 또는 text, photos[최대 5] }
  ① 듣기   기존 hear() 그대로 → 말한 글
  ② 보기   사진 → {gear_type 후보, 부착물, 오염, 담는 방식, 보이는 개수} + 칸마다 확신 정도
  ③ 합치기 코드가 규칙으로 합침
  ④ 게이트 기존 것 + 사진 근거 규칙
  → 초안(칸마다 출처 표시). 사람이 확인해야 저장
```

**무엇을 어디서 읽나**

| 칸 | 말·글 | 사진 | 정하는 규칙 |
|---|---|---|---|
| 무게, 개수, 날짜, 가격 | 예 | 아니오 | 숫자는 말·글에서만. 사진에서 나온 숫자는 "보이는 톤백 약 3개"처럼 추정 주장으로만 내고 칸에 넣지 않음 |
| 어구 종류 | 예 | 예(후보) | 말이 있으면 말. 사진과 다르면 질문 주장("자망이라고 하셨는데 사진은 통발로 보임, 확인 필요") |
| 부착물, 뻘·패각, 젖음 | 예 | 예 | 둘 중 하나라도 '있음'이면 있음. 둘 다 없으면 '모름' |
| 재질(나일론·PE·PP) | 예 | 아니오 | 사진으로 재질을 '확인'으로 올리지 않음. 업체 표본 확인이 원칙(실증안 3절) |
| 위험물(납 봉돌 등) | 예 | 예 | 하나라도 있으면 표시, 기존 hazard 규칙과 같은 취급 |

**코드 쪽**

- `LLMProvider`에 `see(system, user, images, schema)`를 더한다. `claude.py`는 사진 입력을 지원하게 고치고, `mock.py`는 정해 둔 답을 돌려준다(테스트용). Ollama는 사진을 받는 모델을 설정에 적었을 때만 켠다.
- 새 에이전트 `app/agents/sorting/photo.py`. 기존 `vision.py`는 건드리지 않는다(이름만 헷갈릴 뿐 하는 일이 다르다).
- 근거 종류에 `photo`를 더한다(`contracts.py`, `gates.py`). 규칙: `photo` 근거만 있는 주장은 `fact`가 될 수 없고 `estimate`나 `question`이어야 한다.
- 사진 읽기가 꺼져 있거나 실패하면 음성·글만으로 지금처럼 동작한다. `GET /v1/lots/intake/status`가 `{stt, vision}`을 알려 화면이 버튼을 숨긴다(기존 STT와 같은 방식).
- 사진에 사람 얼굴, 선박 번호, 연락처가 찍힐 수 있다. 밖의 API로 보내는 설정이면 화면에서 먼저 알리고, 사진에서 읽은 글자는 기존 개인정보 게이트를 지난다.

**정해야 할 것**: 사진을 Claude API로 보낼지, 서버 안 모델로 볼지. 기존 원칙은 "음성은 밖으로 안 보냄"이다. 서버 안 모델이 그물 종류를 얼마나 맞히는지는 직접 시험해 봐야 안다. 시연은 Claude, 원칙은 설정으로 고를 수 있게 두는 쪽을 권한다.

## 6. 문서 사진 → 문서 자동 작성

### 6.1 다루는 문서

**사진으로 받아 읽는 것**

| 서류 | 근거 | 읽는 칸 | 채우는 곳 |
|---|---|---|---|
| 계량증명서 | 계량법 시행규칙 제4조. 법정 서식이 없어 업소마다 모양이 다름 | 꼭 있는 다섯: 요청자, 계량 일자, 품명·차량번호, 실제중량·총중량, 계량증명업자 이름·주소·연락처. 있으면 읽는 것: 공차중량, 시각 | `shipment_legs.weigh_kg`, `acceptances.shipped_kg` |
| 어구등 인수인계 명세서 | 어구보증금 고시 별지 제6호(수집운반 및 재활용). 보증금제로 반납된 어구를 처리업자에게 넘길 때의 법정 기록 | 상호, 사업자등록번호, 대표자, 주소 / 일자, 인수자, 인계자, 어구 종류·수량(개, 폭), 중량(kg), 재질, 비고 | `acceptances`, `shipment_legs` |
| 폐어구 및 유실어구의 관리대장 | 수산업법 시행규칙 별지 제73호. 시장·군수가 쓰는 집하장 대장 | 종류, 규격, 재질, 형태 / 연월일, 회수량, 처리량, 무게(kg), 미처리량, 비고, 작성자, 결재자 | 지난 반출 이력(6.3) |
| 처리확인서, 청구서·세금계산서 | 용역 검측 서류, EPR 실적 증빙 | 서식 [미확인]. 업체명, 일자, 중량, 처리 방법, 금액 | `acceptances.method`, 정산 비교표 |
| 차량 사진 네 장 | 용역 설계서 예시(공차, 앞면, 실은 뒤, 반입) | 글자를 읽지 않고 붙이기만 | `shipment_legs.photos` |

**받지 않는 것**: 어구보증금 반환증. 반납자 이름·계좌·전화가 들어 있고 보증금 시스템 정보는 고시상 비밀 유지 대상이다. 올리면 "이 서류는 받지 않음"으로 돌려보낸다.

**앱이 만들어 주는 것**

| 문서 | 재료 | 비고 |
|---|---|---|
| 반출분 카드 | 묶음, 사진, 반출편 | 업체가 견적 때 묻는 12가지(4.1-2)를 담음 |
| 조건 확인 요청서 | 반출분 카드 + "그대로 / 떼어서" 질문 | |
| 관리대장 초안 | 묶음 등록과 반출 기록 | 별지 제73호 칸 그대로. 이 서식에는 반출처 칸이 없어 비고에 넣음 |
| 인수인계 명세서 초안 | 인수 결과 | 고시 별지 제6호 칸 그대로. 제출은 회수관리자가 보증금 시스템으로 함 |
| 정산 비교표 | 견적, 인수 결과, 계약 정산 규칙 | 기존 방식과 비교 |
| 분기 실적 요약 | 반출분 집계 | 시·도가 해수부에 내는 분기 실적 칸(종류, 처리 물량 kg, 소각·매립·재활용, 처리업체)에 맞춤 |

폐어구는 생활폐기물이라 올바로(전자인계서) 대상이 아니다 [사실]. 기존 `handover_sections` 3칸은 내부 기록용으로만 쓴다.

삽시도 현장이 실제로 쓰는 장부와 업체의 처리확인서 모양은 공개자료에 없다. `kind`별 칸 목록은 `harness.yaml`에 두어 바꿀 수 있게 한다.

### 6.2 처리 순서

```
POST /v1/scans  { photo, shipment_id 또는 order_id, kind(모르면 비움) }
  ① 옮겨 적기  사진의 글자를 있는 그대로 transcript로
  ② 칸 채우기  kind별 칸 목록에 맞춰 {value, quote(원문 그대로 인용), sure}
  ③ 코드 검산
  ④ draft 저장 → 화면에서 사람이 칸마다 확인·수정
POST /v1/scans/{id}/confirm  → 대상 표에 반영, applied_to 기록
```

**③ 코드 검산** (LLM을 믿지 않고 코드가 확인)

- 칸의 숫자가 transcript에 글자 그대로 있는가. 없으면 그 칸은 비우고 "직접 입력 필요". 법 조문에 쓰는 "원문에 없는 숫자 금지" 규칙과 같은 생각이다.
- 계량증명서: 꼭 있어야 하는 다섯 항목이 다 읽혔는가. 공차중량이 적혀 있을 때만 총중량 − 공차중량 = 실중량을 검산한다(공차는 법정 항목이 아님).
- 손으로 쓴 계량증명서면 "EPR 실적에는 못 씀"을 표시한다.
- 대장·명세서의 무게는 kg, 소수 둘째 자리까지로 맞춘다.
- 날짜가 반출편 날짜와 앞뒤가 맞는가, 업체 이름·사업자번호가 주문의 업체와 같은가.
- 앞 구간 무게와 5% 넘게 차이 나면 표시(기존 허용 오차 값 사용).
- 손글씨이거나 확신이 낮은 칸은 노랗게 표시하고 그 칸의 사진 부분을 같이 보여 준다.

**지키는 선**

- 확인 전 값은 정산, 인수 결과, 인계 서류 어디에도 들어가지 않는다.
- 원본 사진은 지우지 않고, 자동으로 채운 칸은 어느 스캔에서 왔는지 남긴다.
- 앱은 초안까지만 만든다. 올바로나 기관 시스템에 대신 제출하지 않는다.
- 연락처·주민번호 모양은 기존 개인정보 게이트로 가린다. 계약서 사진은 올린 회사와 조율 담당만 본다.

### 6.3 지난 기록 올리기

장부나 지난 정산서를 여러 장 올리면 반출분 이력으로 쌓인다(`status=settled`, 출처는 장부). 이 이력이 4.2의 **기존 방식 비용(baseline)과 지난 인수율**이 된다. 실증안 1주차 과제("최근 반출 1~3건을 장부에서 최종 처리 명세까지 따라가기")를 앱 안에서 하는 셈이다.
